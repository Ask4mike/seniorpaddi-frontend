Chapter 2The big picture

Before looking at any code, it helps to see the whole machine at once. This chapter follows one visit, from typing an address to seeing a page.

A website is a conversation

Every time you open a page, two programs talk to each other:

  • The browser (Chrome, Edge, the browser on a phone) is the program that shows pages. It asks.
  • The server is a program running on a computer somewhere (or on your own computer while you work). It answers.

The question is called a request and the answer is called a response. A request is like a letter with an address on it, for example GET /events ("please give me the events page"). GET means "show me something"; POST means "here is a form I filled in".

An everyday picture

Think of SeniorPadi as a small office. The address on the letter (/login) is like a street address. The route is the person who answers the door at that address. The database is the filing cabinet in the back room. The view is a pre-printed form that the person fills in before handing it back to you.

One visit, from start to finish

Here is what happens when someone types localhost:3000/login, fills in the form and presses Log in. Every page on the site follows this same path; only the route, the data and the view change.

Opening the page (GET /login)

  1. The browser asks for GET /login.
  2. src/app.js first checks whether public/ has a file called login. It doesn't, so the request moves on.
  3. The middleware runs: the session is loaded (src/config/session.js), the user and language are found (src/middleware/locals.js) and a fresh security token is made for the form (src/middleware/csrf.js).
  4. The routes are tried in order until one matches. src/routes/public.js has router.get('/login', ...), so it answers.
  5. That route calls res.render('auth/login', {...}). EJS takes views/auth/login.ejs, fills in the words and the token, and produces plain HTML.
  6. The HTML goes back to the browser. The browser then asks for the files the page mentions (/css/main.css, the font, the scripts) and those come straight from public/.

Sending the form (POST /login)

Pressing Log in sends a second request, POST /login, with what was typed. Figure 2.2 shows its steps. The important idea is the ending: if the details are wrong, the server shows the same page again with an error message; if they are right, it remembers the person in the session and sends a redirect, which tells the browser to go and ask for another page (Home).

Important

The server builds the whole page before sending it. This is called server-side rendering. It is why SeniorPadi works even on old phones and even with JavaScript switched off: the browser only has to show finished HTML. The small scripts in public/js/ just make things nicer (pop-ups, the password eye button); every form still works without them.

Try it yourself

Once you have the site running (chapter 4), open http://localhost:3000/health. This tiny route in src/routes/public.js asks the database "are you there?" and answers {"ok":true}. It is how Render and uptime checkers know the site is alive.
